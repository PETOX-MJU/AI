# 펫톡스 AI

`PETOX-MJU/AI` — 펫톡스의 모델을 **만드는** 저장소.

**상용 배포를 전제로 설계했다.** 라이선스가 걸리는 구성요소는 제품 경로에 넣지 않고,
추론은 전부 온디바이스로 돌린다.

## 설계 원칙

1. **온디바이스 우선.** 서버 추론은 GPU 상시 비용이다. 무료 앱에서 감당이 안 된다.
2. **서버는 선택사항.** 서버가 죽어도 앱의 모든 핵심 기능이 동작해야 한다.
3. **전용 소형 모델 > 범용 대형 모델.** 더 작고, 더 정확하고, 라이선스가 깨끗하다.
4. **개인정보는 기기를 벗어나지 않는다.** 화면 프레임도, 반려동물 사진도.
5. **모델 카드를 직접 확인한다.** 보도자료는 근거가 아니다.
6. **중급기에서 돌아야 한다.** 플래그십 전용 기능은 핵심 경로에 넣지 않는다.

## 아키텍처

```
[안드로이드 앱 / Kotlin]  ─ 전부 온디바이스
 ├ 오버레이 서비스 (WindowManager)
 ├ 앱 감지 (UsageStatsManager) + 대상 앱 화이트리스트
 ├ 화면 캡처 → shorts_classifier.tflite      숏폼 판별
 ├ 반려동물 사진 → ML Kit Image Labeling      유효성 판별 (Dog/Cat)
 │                → ML Kit Segmentation        배경 제거
 │                → 털색 추출 + 견종 템플릿 재색칠   견종은 사용자 선택, 색은 사진에서
 ├ 주간 분석·미션·한 줄 요약                   Kotlin (kotlin_port/)
 └ Room  ─ 사용 로그·코인·캐릭터 성장 (진실의 원천)

[서버 / 선택]  ─ 없어도 앱이 완전히 동작한다
 └ FastAPI + PostgreSQL ─ 계정 동기화·백업만
```

**모델 추론이 서버에 하나도 없다.** GPU 비용 0, 개인정보 전송 0, 오프라인 동작.

### 주간 분석은 앱에서 돈다

주간 분석·미션 판정·한 줄 요약은 **`kotlin_port/` 의 Kotlin 코드가 정본이고 앱에서 실행한다.**
FE 앱은 이 코드를 그대로 복사해 쓴다(`FE android/app/src/main/java/com/petox/screentime`).

처음에는 Python으로 규칙을 만들고 Kotlin으로 이식했다. 이식을 끝낸 뒤 Python 패키지는
같은 규칙을 두 벌 관리하는 부담만 남아 지웠다. 그때 Python 실행값으로 만든 정답 JSON
(`kotlin_port/contracts/examples/`, `fixtures.json`)은 Kotlin 회귀 테스트로 계속 쓴다.

이유는 설계 원칙 2번과 6번이다. 주간 리포트와 미션은 핵심 기능이므로 서버가 죽어도,
네트워크가 없어도 동작해야 한다. 중급기 사용자는 네트워크가 불안정한 경우가 많다.

**BE는 분석을 호출하지 않는다.** BE 범위는 계정 동기화와 백업뿐이다.

## 온디바이스 LLM — 검토했고 도입하지 않는다

한 줄 요약에 생성형 LLM을 쓰는 안을 검토했으나 **기각했다.** 요약은 계속 규칙 기반
템플릿(`kotlin_port/src/main/kotlin/com/petox/screentime/Narratives.kt`)으로 간다.

| 방식 | 기각 사유 |
|---|---|
| Gemini Nano (ML Kit) | 지원 기기가 Galaxy S25 이상·Pixel 9 이상 등으로 좁다. 원칙 6번 위반 |
| 앱 번들 SLM (Qwen 0.5B 등) | 모델 521MB, 추론 중 RAM 약 1.36GB. 중급기에 과하다 |
| 서버 LLM | 원칙 1·2·4번 전부 위반 |

숫자 환각 위험이 구조적으로 없다는 점도 템플릿이 낫다. **AI 요건은 숏폼 분류기가 담당한다** —
직접 학습시킨 전용 모델이고 온디바이스로 돌며 개인정보를 구조적으로 보호한다.

기기 지원 목록은 바뀐다. 재검토한다면 그때 [ML Kit GenAI 문서](https://developers.google.com/ml-kit/genai)에서
현재 목록을 직접 확인하라.

## 저장소 경계

| 저장소 | 역할 |
|---|---|
| **AI** (여기) | 모델을 **만드는** 코드 — 학습, 평가, 변환 + 주간 분석 규칙(Kotlin) |
| **BE** | 계정 동기화·백업 — FastAPI, PostgreSQL. **분석은 호출하지 않는다** |
| **FE** | 모델을 **탑재하는** 코드 — 안드로이드 앱, TFLite 번들, 분석 로직 Kotlin 이식 |

## 구성

| 디렉터리 | 내용 | 착륙지 |
|---|---|---|
| `shorts_classifier/` | 숏폼 화면 판별 (MobileNetV3 → TFLite) | FE |
| `kotlin_port/` | 주간 분석·미션·한 줄 요약 규칙 (Kotlin) | FE (복사) |
| `pet_validation/` | 사진 유효성 판별 명세 (ML Kit, 학습 없음) | FE |
| `pet_template/` | 반려동물 사진 → 견종 템플릿 재색칠 | FE (Kotlin 이식) |
| `experiments/` | VLM 베이스라인 — **제품 경로 아님** | 비교용 |

`experiments/` 의 모델은 성능 비교 기준선일 뿐이다. **배포 대상이 아니다.**

## 데이터 전략

**TDM(정보분석) 면책 조항은 국내에서 아직 입법되지 않았다.** 타사 앱 화면을 긁어
학습시키면 공정이용 판단에 기대야 하고, 상용 서비스에는 안전장치가 없다.

**완화책: 우리가 만든 영상을 우리가 촬영한다.** 팀이 제작한 짧은 영상을 각 앱에 올리고
그 화면을 촬영한다. 분류기가 학습하는 건 영상 내용이 아니라 UI 배치(오른쪽 세로 버튼 열,
하단 캡션 바)라서 자체 콘텐츠로 바꿔도 정확도 손실이 없다.(현재는 그냥 추천 영상 활용하여 학습 추후 실제 배포 시에는
우리가 영상을 제작하여 학습할 예정.)

**단, 이걸로 전부 해결되지는 않는다.** 영상 콘텐츠 문제는 없어지지만 각 앱의 UI 는 화면에
그대로 남는다. 실무 위험은 낮으나 상용 배포에서는 자문 항목이다 — 세 층위 분석은
[LICENSING.md](LICENSING.md) 참고.

반려동물 사진은 학습에 쓰지 않는다. ML Kit 이 유효성 판별을 하므로 데이터셋이 필요 없다.

`datasets/` 는 **절대 커밋하지 마라.** `.gitignore` 처리돼 있다.

## 캡처 제약 (필수)

화면 캡처는 사용자 본인 화면을 본인 동의로 찍는 것이라 그 자체는 문제없다.
쟁점은 캡처한 것을 어떻게 다루느냐다. 아래는 설계 요구사항이지 권고가 아니다.

### 1. 대상 앱 화이트리스트

**유튜브·인스타그램·틱톡이 포그라운드일 때만 캡처한다.** 다른 앱으로 전환되면 즉시 중단.
카카오톡·뱅킹·메모 화면은 애초에 찍히지 않아야 한다.

```
foregroundPackage in TARGET_PACKAGES  →  캡처 진행
그 외                                  →  캡처 중단
```

법적 리스크를 엔지니어링 제약으로 바꾸는 가장 확실한 방법이다.
**나중에 붙이면 빠뜨리기 쉬우니 스파이크 단계부터 넣어라.**

### 2. 프레임은 메모리에서만
디스크 저장 금지, 서버 전송 금지, 판별 직후 폐기.

### 3. 데이터셋 비공개
팀 외부 배포 금지.

### 4. 앱 내 고지
화면 캡처 사용 사실과 "기기 외부로 전송하지 않음"을 명시한다.

### 5. 미성년자 동의
**만 14세 미만은 법정대리인 동의가 필수.**

## 산출물 전달

`.tflite` 는 git 에 커밋하지 않는다. GitHub Releases 로 배포한다.

```
gh release create v0.1.0 shorts_classifier/build/shorts_classifier.tflite \
  --title "모델 v0.1.0" --notes "숏폼 정밀도 xx%, 재현율 xx%"
```

**학습해서 배포하는 모델은 숏폼 분류기 하나뿐이다.** 반려동물 쪽은 ML Kit 이 전부 처리한다.

FE 는 릴리스에서 받아 `app/src/main/assets/` 에 넣는다.

### 에뮬레이터로는 검증이 안 된다

시연은 에뮬레이터로 해도 되지만 **위 표의 항목을 에뮬레이터로 통과 처리하지 마라.**

| 항목 | 에뮬레이터에서의 한계 |
|---|---|
| `UsageStatsManager` | 실제 사용 기록이 없다. 더미 데이터 주입이 필요하다 |
| MediaProjection 백그라운드 유지 | 제조사 배터리 최적화가 없어 실기기와 결과가 다르다 |
| `FLAG_SECURE` | 실기기의 유튜브·틱톡과 동작이 다를 수 있다 |
| 추론 지연·배터리·발열 | 측정 자체가 무의미하다 |

특히 **제조사 배터리 최적화는 중급기에서 더 공격적이다.** 에뮬레이터에서 멀쩡하던
백그라운드 서비스가 실기기에서 죽는 건 흔한 일이고, 타겟이 중급기라면 이걸 먼저 확인해야 한다.

시연용 에뮬레이터는 Play Store 포함 이미지를 써야 유튜브·인스타 화면이 나온다.
더미 사용 기록 주입 경로는 **debug 빌드에만** 둔다.
